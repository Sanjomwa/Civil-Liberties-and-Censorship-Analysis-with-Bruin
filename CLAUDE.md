This file orients any future Claude session working in this folder. Read it first, before opening anything else.
**Naming note (2026-07-06):** the GitHub repository is named `Civil-Liberties-Intelligence-Observatory` (github.com/Sanjomwa/Civil-Liberties-Intelligence-Observatory), spelled out in full rather than the bare abbreviation, since GitHub repo names only permit ASCII letters, digits, `.`, `-`, and `_` and a bare acronym read as too terse on its own. **"CLIO" / "clio" remains the accepted, expected shorthand** in conversation, commit messages, comments, and documentation — both names refer to the same project. ## What CLIO is, in one paragraph

CLIO (Civil Liberties Intelligence Observatory) fuses internet-censorship measurement (OONI), conflict event data (ACLED), and platform/legal takedown-pressure signals (Google Transparency Report, Lumen Database) into attributed, confidence-qualified findings about civil-liberties pressure. It is a Bruin-orchestrated BigQuery pipeline (raw → staging → intermediate → features → intelligence → marts → reporting) with a read-only Streamlit dashboard on top.

## The project has two completed phases behind it — know which one you're in

1. **The Constitution Project** (complete, frozen, historical context only). A philosophical/scientific inquiry into what CLIO's recurring engineering patterns might imply about evidence, uncertainty, and reasoning as a general discipline. Its conclusion, stated plainly by its own final document: CLIO is not currently a general reasoning architecture, most of what looked novel reduces to existing fields (metrology, database provenance theory, psychometrics, epistemology), and further progress requires operational evidence, not more theory. **Do not extend, rewrite, or treat these documents as implementation specifications.** They now live in `clio_constituion_project/` at this folder's root (moved there by the project owner, not by any automated process): the eight `.docx` files from Deliverable 1 through the Executive Summary. Indexed, not duplicated, at `docs/04-research/README.md`.
2. **The CLIO Project Zero Review** (complete). The first implementation-focused review — technical, product, commercial, strategic, and competitive assessment of the actual repository and business documents, plus the `docs/00-06` documentation structure this project now uses. Lives at `CLIO_Project_Zero_Review.docx`, with its commercial/product content split into `docs/01-product/` and `docs/05-business/`.
3. **The CLIO Engineering Reset** (this phase, current). From here forward, CLIO is first and foremost a software engineering project. The Constitution explains why certain ideas exist; it does not dictate what to build. Engineering decisions come from the current codebase, the product goals, and evidence gathered during implementation.

## Public repository docs policy

Decided 2026-07-12. Of the numbered `docs/` folders, only `docs/02-architecture/` and `docs/03-development/` are intentionally public. Every other numbered folder — `docs/00-overview/`, `docs/01-product/`, `docs/04-research/`, `docs/05-business/`, `docs/06-operations/`, `docs/07-governance/` — is internal planning or governance material and must never reach the public repository. This is a blanket rule at the folder boundary, not a rule limited to files that happen to self-declare as private (e.g. `docs/07-governance/licensing-compliance-register.md`, called out by name in ADR-0007 as "a private governance document, not published in this repository") — a harmless-looking file in one of these folders (a frozen research index, an empty operations stub) is still covered, on the theory that the boundary should fail safe rather than rely on someone remembering to flag each file individually.

Enforcement is `.gitignore` folder-level rules (`docs/00-overview/`, `docs/01-product/`, `docs/04-research/`, `docs/05-business/`, `docs/06-operations/`, `docs/07-governance/`), not per-file globs — a per-file pattern (e.g. matching only dated filenames) silently admits any new file that doesn't match its exact shape, which is exactly the failure mode found and fixed 2026-07-12: a stale glob covered only `docs/01-product/2026-07-11-*.md`, leaving `docs/01-product/README.md` untracked-but-not-ignored and one keystroke away from a careless `git add -A`. Before trusting this boundary, verify it directly (`git status --ignored`, `git check-ignore -v <path>`) rather than assuming it holds — `git ls-files` showing a folder absent is necessary but not sufficient, since untracked and ignored are different states.

This project maintains a second, separate copy of this file in a planning environment; this section should stay in sync between both copies, per the same discipline already established for `decision-log.md` across environments (see "Engineering principles" below).

## Engineering principles for this project

Prefer understanding over speed. Prefer architectural consistency over local optimization. Minimize unnecessary complexity; do not introduce an abstraction before at least two concrete cases justify it. Document every significant engineering decision as an ADR. Preserve historical reasoning where useful, but do not let a historical document dictate an implementation choice if better evidence exists now. If an existing design is already good — the OONI evidence/interpretation separation, the ACLED path A confidence/risk split, `streamlit/core/contracts.py` — preserve it and say so; do not rewrite something that already works. If something should change, name exactly why, with a file and line reference, not a general impression.

**Treat a bug report's proposed fix as a hypothesis, not an instruction.** As of 2026-07-05, this has been confirmed five separate times in this project (ADR-0002 step 5, TD-40, TD-02, TD-01's consumer chain, ADR-0001/TD-05): the originally-documented fix was wrong in a way that direct investigation of the actual schema/grain/consumer chain caught before any code was written. Spend the five minutes verifying the bug's actual shape before writing the diff, every time — it has never once been wasted effort in this project so far.

**Update this repository's own tracked docs (`technical-debt-inventory.md`, the relevant ADR, `implementation-roadmap.md`, and `decision-log.md`) in the same commit as the fix that resolves them — do not leave that for a separate pass.** This is now the standing expectation for every session working in this repo, not a one-off instruction. It closes a real failure mode this project hit more than once early on: planning documents drifting out of sync with the live repo, requiring manual re-copying to fix.

`decision-log.md` is explicitly included in that list, not just the ADR files — it was omitted from an earlier version of this instruction, and that omission is the confirmed cause of a real sync gap (2026-07-05): the file went stale in the live repo (a bare 9-line ADR index, missing ADR-0002/0003/0004 and this file's entire "Narrative decision log" section) because every prior fix updated its own ADR but nothing ever touched `decision-log.md` itself. Two things follow. First, whenever a commit resolves or materially revises anything `decision-log.md`'s ADR index or narrative section describes, update both the index row and add or amend a narrative entry in the same commit — do not treat the narrative section as historical-only or as someone else's file to maintain. Second, if a decision or reasoning step originates in a planning conversation rather than in this repo (e.g. an ADR drafted before any code changes exist to carry it in), whoever next touches this repo to implement or reference that decision should carry the relevant `decision-log.md` content into the live file as part of that commit, rather than assuming it already made it across.

**This file's own "Facts every session should know" section is a deliberately curated highlight reel, not a continuously-synced log — unlike the four files named above, it is not included in the "update every commit" list.** Decided 2026-07-06, after noticing this section had gone stale (last updated 2026-07-05, missing TD-41 onward and ADR-0003 through ADR-0006) despite `decision-log.md`, `technical-debt-inventory.md`, and `implementation-roadmap.md` all staying current in the same window — the same blind spot that once caused `decision-log.md`'s own gap, except this file never got the equivalent fix for itself. Rather than add a fifth file to an already-fragile synchronization requirement (this project's own TD-57 already tracks the general risk of keep-in-sync duplication, just applied to SQL there instead of docs), the deliberate choice is one authoritative, continuously-updated narrative (`decision-log.md`'s "Narrative decision log" section) plus a short, honestly-incomplete index here. **If something isn't mentioned in the Facts section below, check `decision-log.md` before assuming it wasn't done** — recent entries there are the actual source of truth for what has happened in this project, not this file's bullet list.

**Model-routing policy (added 2026-07-06): default to the cheapest capable model as executor; call a stronger reasoning model only in a narrow advisory role, not as the default driver of a whole session.** Adopted from an observed pattern (an executor model does the bulk of file reads, tool calls, and writing — the token-heavy part — while a stronger model is consulted only at specific judgment points, so most tokens bill at the executor's lower rate). This is a direct extension of "treat a bug report's proposed fix as a hypothesis" above, just re-routed onto which model performs the verification: rather than the executing session reasoning out its own verification of a claim, it should raise a narrow, specific question to an advisory call — "here is the proposed fix and the file/line; is the diagnosis actually correct against the live schema/consumer chain" — and only proceed once that comes back confirmed or corrected. Concretely: default every Claude Code session to Sonnet 5 (or whatever is the standard-tier model at the time) as executor. Escalate to an advisory call on a stronger reasoning model at the moment a diagnosis needs checking before code is written, not for the whole task — either via a mid-session `/model` switch and back, or a dedicated subagent (`.claude/agents/advisor.md`) pinned to the stronger model via its frontmatter (not yet built in this repo as of 2026-08-16 — see below). Reserve a stronger model as full executor only for genuinely novel, high-blast-radius, multi-day-scope builds — the same threshold this project's own backlog-tiering policy already uses for Tier 3 work (see `decision-log.md`). This policy also governs the separate Cowork planning environment this project uses — since that environment maintains its own copy of this file, keeping both in sync is the same discipline already established for `decision-log.md` above.

**Amendment (2026-08-16): Opus 4.8, not Fable 5, is the default advisory-tier model for per-fix diagnosis checks.** Fable usage has a real cost ceiling worth conserving, and most per-fix diagnosis checks — "here is the proposed fix and the file/line; is the diagnosis actually correct against the live schema/consumer chain" — don't need Fable's specific strength; Opus 4.8 is adequate at the frequency those checks actually happen. Fable is reserved for exactly two narrower situations instead: (1) genuine novelty, a judgment call this project has no established precedent for, not just any diagnosis check; (2) a deliberate audit pass run after a milestone completes, reviewing accumulated work as a whole rather than any single fix in isolation. Everything else about the policy above is unchanged — Sonnet 5 stays the default executor, the escalate-on-a-narrow-question mechanism is unchanged, and the Tier-3 full-executor exception is unchanged; only the advisor-tier default model name was stale.

## Claude Code prompting standard — no autonomous commits or pushes

**No-commit/no-push, by design — not a technical default that gets relaxed once trust is established.** Any relay prompt or direct Claude Code session working in this repository must not run `git commit` or `git push`, and must not draft suggested commit-message text. A session's job ends at making changes, verifying them, and reporting factually what was done and found; the project owner (Sam) reviews and commits by hand. This is a deliberate choice about whose hand is on the actual mechanism of record.

**Findings go to `reports.md` at the repo root — ephemeral scratch, not a durable record.** It must be listed in `.gitignore` (confirm with `git check-ignore -v reports.md` before writing to it, rather than assuming the rule still holds — see the "Public repository docs policy" section above for why this project verifies `.gitignore` coverage directly instead of trusting it by memory) so it can never be staged or committed by accident. Sessions overwrite it at the start of their own report rather than appending to it, so it contains only the current session's findings when the session ends — but `reports.md` itself is not the durable record; that role belongs to `decision-log.md`, the ADRs, and `technical-debt-inventory.md`, all updated and committed by hand from what a session writes here.

**All materialization in this repository goes through `Bruin/scripts/safe_run/safe_materialize.py` — a bare `bruin run <asset>` is not a sanctioned command for a fix session.** It always cascades (`bruin run --downstream`) and runs the ADR-0005 staleness check in the same invocation, so a partial-cascade mistake (the exact shape behind TD-38, TD-40, TD-54, and the 2026-08-16 staleness-check failure) surfaces in the same session instead of in next-day CI. See [ADR-0012](docs/02-architecture/adr/0012-cascade-safe-materialization-no-scheduled-run.md) for the reasoning (why a scheduled daily `bruin run` was rejected as the fix) — this is only the pointer.

**Any session that rematerializes CLIO's OONI verdict chain (`stg.ooni_measurement_summary`, `int.ooni_measurement_verdicts_candidate`, `int.ooni_measurement_verdicts_confirmed_guard`, `int.ooni_measurement_verdicts`, or anything downstream of them) should dispatch the `ooni-agreement-check.yml` workflow, or run `Bruin/scripts/agreement_check/ooni_agreement_check.py` locally, as part of its own verification obligations — not just `bruin validate` and the test suite.** This mirrors `safe_materialize.py`'s own printed reminder (TD-100/ADR-0013, steps 1-4): CLIO has caught three real problems with these classifications by accident (TD-68, TD-93, and a third dnscheck finding), never by a standing check, so a session touching this layer should treat an agreement-check run as part of confirming the work, the same way the staleness check is already part of confirming a cascade. **The workflow's weekly cron is permanently disabled by explicit project-owner decision, not merely not-yet-enabled** (ADR-0013, updated 2026-08-30): CLIO is still pilot-stage on a historical backfill, not continuously ingesting live data, so a fixed weekly timer would mostly spend OONI's own rate-limited public API budget re-confirming an unchanging result. `workflow_dispatch` (manual, or triggered per the paragraph above) is the only mechanism in effect, indefinitely — do not treat enabling the cron as a pending follow-up item.
